# speedrun.fog

The `/speedrun` page (navbar item "Speedrun", formerly the `speedrun.fog` tab of `/stats`, whose `?tab=speedrun` URL redirects to it, whatever else the query holds) is a speedrun.com style game page: game header card (hidden on phones, where it would fill the first screen; its Discord and Website links are the navbar's Discord icon and `/about`), category pills, Set Seed and Random Seed subcategories, ranking table, side column with game stats and recent personal bests, in SpeedFog's colors. Set Seed replays put several runners on the same seed, which makes their times comparable across runs; Random Seed ranks blind runs only.

Each category (a pool) has two boards, **Set Seed** and **Random Seed**, plus a **Deathless** filter. Computed in `services/speedrun_service.py`, served by `api/stats.py`.

**Run modes.** `RunMode` (`normal`, `speedrun`, `set_seed`) is set when a race or a solo session is created and never changes. The migration `c3a9d71e5b24` makes every existing race and session `normal`: the boards count normal races, so the community races finished before modes existed keep their runs. Race and session responses (`RaceResponse`, `RaceDetailResponse`, `TrainingSessionResponse`, `TrainingSessionDetailResponse`) carry it as `mode`. In game, a `set_seed` race or session names every fog gate's destination in the mod overlay (the boss behind it included), visited or not, since the player knew the seed beforehand; the other modes show `???` until the destination is visited (`reveal_exits` of `compute_zone_update`, see `zone_update` in `PROTOCOL.md`).

**Which runs are counted.** A participant with status FINISHED in a race that has a seed and is itself FINISHED, whose user is not banned. Every mode counts: community races (`normal`, `speedrun` or `set_seed`), Daily Seeds and event races (qualifiers and playoff races). Three kinds of race never count (`race_unranked_reason`, the Python rule, and `counts_on_boards_clause`, its SQL twin in `load_counted_runs`, kept in step): a race that drew a SEEN seed (`Race.seed_was_seen`, see "Ranked races" below), whatever its kind; a community race in `normal` mode reset after its start (`Race.seed_played`, set by the reset and cleared by a reroll; its runners replay a seed they played, so the second attempt is not blind, and only a reroll with a seed report puts the race back on the boards, see below; an event race's reset is the admins' call and keeps it on the boards, a Set Seed race is a replay anyway, and a speedrun race cannot be reset); and a community race, `normal` or `speedrun`, whose seed was re-rolled without a seed report (`Race.rerolled_without_report`, set by `reroll_seed_for_race` and never cleared). Its organizer may have looked at the seed it gave up (the starting class once the pack is downloaded, or the map, which the race's live data carries in SETUP) and kept rerolling until a good one came up, so the seed it kept is no blind draw. A speedrun race must count, so its reroll always carries a seed report: `reroll_seed_for_race` refuses one without a report or with a blank reason (400 "A speedrun race's seed re-roll needs a seed report with a reason"), every seed it gives up (a discarded pool's aside) reaches the admins' Reported Seeds list, and only a speedrun race rerolled unreported before reports were required carries the flag. A reroll with "Report this seed as buggy" checked does not take the race off the boards (the reported seed goes to the admins, so an abuse shows), and so does the reroll that gives up a seed SEEN when drawn: that seed could not count, so the reroll only gives the race its first countable seed, as a creation would; any later unreported reroll takes the race off. A played seed (a reset race's) could not count either, but its reroll is no exception: start, reset and reroll would fish as well as any reroll, so only a reported one puts a reset race back on the boards. The admins reroll Daily Seeds and event races, which keep counting. Races rerolled before this rule shipped keep counting (no backfill, as for resets). Deleting a race and creating another still gets a fresh seed: the rule makes fishing slower, not impossible. `RaceDetailResponse` carries the reason as `unranked_reason` (null when the race can count; with several, the re-rolled race's comes first since nothing clears it, then the seen seed's, then the reset's), and the race page shows it under its header: "Seen seed: another race drew this seed and gave it up, so its map may be known and this race does not count on the Speedrun boards. A race gets such a seed when its game mode runs low on fresh ones." or "Reset race: its runners already played this seed, so this race does not count on the Speedrun boards." or "Re-rolled race: its seed was re-rolled without a seed report, so this race does not count on the Speedrun boards." The race's Re-roll Seed window says "Without a seed report, this race will count on no Speedrun board." under its report checkbox while the box is unchecked, on a normal community race that counts today or was reset (`RaceDetailResponse.unranked_code` null or `reset`; the code, `seen_seed`, `reset` or `rerolled`, comes with `unranked_reason`), and the Reset Race confirm says so under the same condition. On a speedrun race the window has no checkbox: a "Reason for the re-roll" field takes its place, with "A speedrun race's re-roll goes to the admins as a seed report, so the race keeps counting on the Speedrun boards." under it (only "A speedrun race's re-roll goes to the admins as a seed report." on a race already off the boards for a reroll), and Re-roll with the field blank shows "A reason is required." and keeps the window open. Public and private races both count. Pools whose config `type` is `training` never appear. Finished solo sessions in `speedrun` or `set_seed` mode (`TrainingSession.mode`) also count, as run type `solo`, under the same pool and layer-count rules; `normal` sessions never do. A run is `blind` unless it is a Set Seed replay (a race or session whose mode is `set_seed`), the runner having known the seed beforehand. Only seeds at the pool config's current `layers_count` count (a seed with another `total_layers` stays out), which stands in for "the current version of the pool": seeds generated before the fixed layer counts of May 2026 varied in depth (Standard ran from 17 to 38 layers), so most of them drop out, though an old seed that landed on the current count still counts. Changing a pool's layer count restarts its board, like a new game version on speedrun.com; to keep the old board viewable, the operator adds the old count to the pool TOML's `[display] archived_layers` and rescans the pool (see Archives below). A pool whose config has no `layers_count` keeps every seed. Only seeds added (scanned, `Seed.created_at`) since `SPEEDRUN_BOARD_START_DATE` count, 2026-09-01 by default: the pools were regenerated for Elden Ring 1.17 then, after the generator stopped clamping enemy scaling at tier 21, so the boards start on seeds that play like today's, with two months of history at their launch. Unlike `SET_SEED_MIN_SEED_DATE`, this date is not raised on a game patch. A run on an older seed stays on its race page and its seed page (a seed page lists its runs whenever the seed was added), and a pool whose runs are all older has no category. Requiring a finished race keeps a running Daily Seed or an open qualifier out until it ends, so the board never reveals the deaths or weapons a running daily hides.

**What each board counts.**

| Board       | Counts                                                                                                                                                              |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Set Seed    | Every counted run, blind and replay, of every run type (`race`, `daily`, `event`, `solo`), except on an excluded or too old seed (see below).                       |
| Random Seed | Blind runs only: runs whose seed the runner did not know beforehand (mode is not `set_seed`, for races and sessions alike). Empty when a category only has replays. |

A run is on the Set Seed boards (`CountedRun.on_set_seed_boards` in `services/speedrun_service.py`) unless its seed was excluded by an admin (see Admin exclusion) or added before `SET_SEED_MIN_SEED_DATE`. A purged seed (its zip is gone) keeps its runs there: deleting files to free space does not undo a run. Each row carries `replayable`, true when its seed can still be played in Set Seed: it has no `set_seed_block` (carried by each counted run: `excluded`, `old_game_version` or `purged`, the zip checked once per seed each time the counted runs are loaded, so a purge shows on the boards within one cache TTL) and is not in an archive (whose seeds have an older layer count). The seed page's replayability reads the same verdict (`seed_replayability`), and a seed page's rows all carry the page's own `replayable`. A blind run in progress hides a seed page's runs (`in_progress`) but leaves the board rows' `replayable` alone; the layer count is not part of `set_seed_block`: it picks the seed's category, an archive included. Random Seed keeps blind runs whatever their seed's state: nobody replays them there. Raising `SET_SEED_MIN_SEED_DATE` after a game patch thus restarts every Set Seed board on its own.

A run's `blind` flag is exposed on every row, so a Set Seed board can mark which runs were blind. The Deathless filter (`deathless=true`) keeps only runs of races with the deathless option (`Race.deathless`) and so never includes solo runs. It combines with either board. The default boards include deathless races.

**Archives.** A pool can declare older layer counts worth keeping a board for in its `config.toml`, `[display] archived_layers = [25, 22]` (racing-only: the seed generator never reads it). `_normalize_pool_config` stores it as a list of ints under `archived_layers` on `Pool.config`; a value that is not a list gives `[]` and non-int items (booleans included) are dropped one by one. A counted run whose seed's `total_layers` is in that list (and is not the current count) belongs to the category `<pool>@<layers>` (e.g. `standard@25`, served by `GET /api/stats/speedrun/standard@25`); a seed at any other non-current count stays out, as before. An archived category is always retired, is named `<Pool display name> (<layers> layers)` and is released at its earliest seed at that count; it is listed only while it has counted runs.

**Categories.** One per pool with at least one counted run at its current layer count, plus the archives above: enabled pools by `sort_order` (pools without one last), then disabled (retired) pools in the same order. A category's `released_at` is its earliest seed at the current layer count (any seed without `layers_count`) added since `SPEEDRUN_BOARD_START_DATE`; the History list opens with it ("Boss Rush was released"). The category key of a board is the pool name, or `<pool>@<layers>` for an archive; a recent run's `pool` carries that key.

**Ranking.** A board is a category, a `sub` (`set` or `random`), the Deathless filter and a set of run types. Each player keeps their best run (lowest IGT, the earliest on a tie). Equal IGT shares a rank and the next rank skips (1, 2, 2, 4). With obsolete runs requested, every run of the board is listed by time and the runs that are not their player's best carry no rank. The record history lists, in date order, each run strictly faster than every earlier one; the web side words it like speedrun.com's history list (a new holder "set a new record time" and shows the gain on the previous record, a holder beating their own record "improved their time"). The recent runs (`recent_runs`, the Recent PBs panel) are personal bests on their category's Set Seed board (all run types, Deathless filter off): a run is one when it is strictly faster than every earlier run of its player there, or its player's first run there; a slower run or a tie is left out, and so is a run on no Set Seed board (an excluded or too old seed). A run on a purged seed stays on the board, so it can be a personal best and still keeps its player's later, slower runs out. A recent run's place is its place on that board: 1 + the number of other players whose best there is strictly faster.

**Record seed.** A board response carries `record_seed`: the seed of its first ranked row (the record), how many runs of the board, obsolete ones included, are on that seed, and `replayable`, the record row's own `replayable` (see above): false for a Set Seed record on a purged seed, in an archive, or for a Random Seed record on a seed that cannot be played in Set Seed. `null` on an empty board.

**Weapon** (the "Route" column, after speedrun.com's Elden Ring boards; its header's tooltip reads "Main weapon used"). The combo held for the most ticks over the run (summed `zone_history` weapon ticks, base ids), the same id coercion as `/weapons`. Runs from before weapon tracking have none. It is decoded only for the rows a response returns, never for the whole run list.

**The page.** `/speedrun` (header "Speedrun" with a gold "Beta" badge and a three-sentence introduction: which runs count and how they are timed, then what Set Seed and Random Seed rank; `web/src/routes/speedrun/+page.svelte`, state in `web/src/lib/speedrun.ts`) mirrors its state into the URL so a board can be shared: `pool`, `sub=random` (Set Seed is the default and stays out), `deathless=1`, `types`, `obsolete=1`, `view`. The old `sub=any|deathless` values read as Set Seed. A board shows the category pills, then the "<Category> - Subcategories" segmented control (Set Seed / Random Seed), then the **WR seed band** (a gold-tinted strip: "WR seed" chip, the record's seed linking to its seed page focused on the record run, its time, the holder, a Blind or Replay chip and "N runs" from `record_seed`, then "Play seed" when the record's seed can be replayed (`record_seed.replayable`), which opens the Start a run window in Set Seed mode with that seed typed in; absent when `record_seed` is null or beside a load error, and kept in place but hidden and inert while another board loads, so the toolbar and its open Filters popover do not move), then the toolbar. Filters lists Races, Daily Seeds, Event races, Solo runs, "Deathless only" and "Show obsolete runs". The Rules button shows what Set Seed and Random Seed are (Set Seed: every run, blind or replayed, except on a seed an admin excluded, any seed replayable as often as you like while its files are kept on the server, a struck-through seed no longer; Random Seed: blind runs only, on a seed nobody had played), then the Speedrun rules, then the category's description, duration and mode rules. The streamer tools sit in a "Tools" menu, hidden on phones and shown with "Start a run" when a category is selected: "OBS overlay" (see OBS overlay below) and "LiveSplit splits", the category's splits file (see `docs/LIVESPLIT.md`); a pick closes the menu, and so do a click outside it and Escape. "Start a run" opens the Start a run window (see "On the web" under Starting a ranked run). The **Run column** (Blind or Replay chip) shows on the Set Seed board only. Every Blind or Replay chip (board rows, WR seed band, seed page rail) has the same tooltip, `RUN_KIND_TITLES` in `web/src/lib/speedrun.ts`: "The runner did not know the seed beforehand" or "Set Seed run: the runner may already know the seed". The Seed cell, and the WR seed band's seed, grey out and strike through a seed that can no longer be replayed (`replayable` false, tooltip "No longer replayable"). A seed links through `speedrunSeedHref`: its seed page, focused on that run (see The web page below). A record history time links the run's own page instead (`speedrunRunHref`): a record is a moment of a race. The side column opens on the active speedrun and Set Seed races (`GET /api/races?status=setup,running&mode=speedrun,set_seed`, loaded once with the page; a failed load only leaves them out), all categories together: "Live races" (running, in the API's order), then "Upcoming races" (in setup with a scheduled date, soonest first; an undated one is left out, as on `/races`), each group hidden while empty. Each race is a `RaceCard` in its `narrow` variant (`variant="narrow"`): the name, a short seed-type chip ("Random" for a speedrun race, "Set Seed", from `RunModeChip`'s `short` option), the game mode and a deathless race's `DEATHLESS` tag (wrapping to its own line beside a JOIN strip), the date on its own line ("Started 25m ago", or the scheduled time), the avatars, the casters of a running race, and the JOIN strip while the viewer can join; the card links to the race page. A run of the side column's "Recent PBs" panel reads "Blind" or "Replay", plus " · Deathless" for a deathless run, then its weapon. Under that panel, a small line reads "This page deliberately parodies speedrun.com. SpeedFog is not affiliated with it.", speedrun.com linking to the site.

**Most practiced seeds.** The side column's "Most practiced seeds (<N> days)" panel lists the `SPEEDRUN_PRACTICED_SEEDS_COUNT` (5) Set Seed seeds with the most attempts in the last `SPEEDRUN_PRACTICED_SEEDS_DAYS` (7) days, the window riding on the overview as `practiced_seeds_days` so the label never repeats the number, all categories together (`practiced_seeds` of the overview, computed by `load_practiced_seeds`). An attempt is a `set_seed` solo session created in the window (invalidated sessions out) or a participant of a `set_seed` race who joined in it (`Participant.created_at`), whatever its status, finished or not; banned users and training pools are left out. Seeds sort by attempts, then distinct players, then seed number. A row reads "<first 6 characters of the seed> · <category name>" with "<n> attempts · <m> players" (singular for 1) and links to the seed page; the panel is hidden when nothing was practiced. It rides on the overview's 15-minute cache.

**OBS overlay.** The "OBS overlay" entry of the board toolbar's Tools menu opens a settings window that builds the URL of `/overlay/speedrun/<pool>`, a transparent leaderboard for an OBS Browser Source in the style of the race leaderboard overlay (badge in place of speedrun.com's flag, name template kept). It shows the board on screen, personal bests only (never obsolete runs): the category, `sub=random` for Random Seed (Set Seed is the default and stays out), `deathless=1` for the Deathless filter and the `types` filter, under the page's own parameter names. The settings window builds the URL from the board currently shown (its `sub` and `deathless`), and the overlay reads them to fetch the matching board. `top` rows (default 3) stay fixed from first place; `cycle` rows (default 3) page every 6 seconds through the players after them, up to rank `until` (default 20, players tied at that rank included); `player` (a Twitch username, matched whatever its case, prefilled with the viewer's own) pins that player's row at the bottom, set apart, with a gold time. A pinned player already in the top gets the gold time in place instead, and never also shows in the cycle; a player without a run on the board gets no row. Default values stay out of the URL. The overlay refetches the board every 5 minutes (every 30 seconds until a first load succeeds), so a new personal best shows within 5 minutes of the finish of its race or session, which refreshes the cached boards at once (see Cache keys). The row split lives in `speedrunOverlayRows` (`web/src/lib/speedrun.ts`).

**Endpoints.** `GET /api/stats/speedrun` returns the categories, the run and player counts and the `SPEEDRUN_RECENT_RUNS_COUNT` most recent personal bests (5 by default, see Ranking). `GET /api/stats/speedrun/{category}?sub=set|random&deathless=<bool>&types=<race,daily,event,solo>&obsolete=<bool>` returns one board, its record history and its record seed; `sub` defaults to `set` and anything else is 422, `types` must be a non-empty subset of the four (422 otherwise) and a category without counted runs answers 404. The seed page endpoints live under `/api/speedrun` (see Seed page below).

**Cache keys.** Both endpoints sit behind the stats cache; the counted run list itself is cached once (`speedrun:runs`, light columns only) and every board key (`speedrun:board:<category>:<sub>:<deathless>:<types>:<obsolete>`) derives from it. A board is cached as its serialized JSON bytes rather than a response model: with obsolete runs shown it lists thousands of rows, and one bytes object adds nothing to garbage-collection passes nor needs serializing on each hit. A Set Seed exclusion or its removal drops every `speedrun:` key at once (`forget_speedrun_caches` in `api/stats.py`), so the boards change without waiting for the TTL. A counted finish (the record check below runs only for a race or ranked solo session that can count, and stops when none of its runs does) shows at the next request too, record or not, without reloading every counted run (about 1.4 s of event loop at 42k runs): the check loads its pool's runs fresh anyway, and `replace_speedrun_pool_runs` swaps them for that pool's runs in the cached `speedrun:runs` (archives included) and drops the overview and board keys, which rebuild from the list in memory. The list keeps its expiry, since the other pools' runs are no fresher; with no list cached, only the derived keys go. A stats cache value computed while a writer dropped or replaced keys of its group (the part of the key before its first `:`, here `speedrun`) goes to its caller but is not cached, so neither a board built from the list before the swap nor a refresh of the list that started before the finish's commit can pin an older board for a whole TTL. A swap whose load overlapped another write (two counted finishes checked at once, whatever their pools, an exclusion or a solo run invalidation) cannot tell which is newer and drops every `speedrun:` key instead; the check reads the generation (`speedrun_cache_generation`) before its load.

**Record announcements.** `services/speedrun_records.py` posts each new record to the records Discord webhook (`notify_speedrun_record`; `DISCORD_RECORDS_WEBHOOK_URL`, else `DISCORD_SPEEDRUN_WEBHOOK_URL`, else the main one, see `DISCORD_BOT.md`). `fire_race_finished_notifications` (the finish of a race that can count, `race_counts_on_boards`) and `TrainingModHandler._handle_finish_event` (Speedrun and Set Seed sessions only) schedule `check_speedrun_records` as a background task, off the request path. It loads the counted runs of the finish's pool fresh (`load_counted_runs(pool=...)`: a finish cannot change the boards of another pool, and the full reload cost about 1.4 s of event loop at 42k runs), takes the finish's own runs and, per category and board (Set Seed, or Random Seed for blind runs), compares the fastest of them with every other counted run (all run types, Deathless filter off, runs on an excluded or too old seed out of the Set Seed board, runs on a purged seed in). Only a strictly faster time is a record; a first run on an empty board is one too. Announcements are remembered by `(category, sub, run id)` in process memory (bounded; cleared past 5000 entries), so a repeated finish notification is silent; a restart between two checks of one finish may announce again. An invalidation never retracts a post.

## Seed page

`GET /api/speedrun/seeds/{seed}` (router `api/speedrun.py`, rules in `services/set_seed_service.py`) serves the page of one played seed: its runs, its map, whether it can be replayed in Set Seed and what keeps its files.

**Which seeds have a page.** `{seed}` is the full seed number or a prefix of at least 6 characters (trimmed, any case). Only known seeds answer: not AVAILABLE, not from a training pool, with a race RUNNING or FINISHED on it or a solo session in `speedrun` or `set_seed` mode (any status). A SEEN seed (shown before its race started, then put aside) is unknown until a race plays it. Any other seed answers 404 "Unknown seed" and never makes a prefix ambiguous, so no response reveals an unplayed seed. A prefix matching several known seeds answers 409 "Ambiguous seed ID". The protection and admin exclusion endpoints below take the seed the same way.

**Public.** A known seed's page is public once no blind run on it is in progress: no race whose mode is not `set_seed` in SETUP or RUNNING on it (Daily Seeds, event races and async races included), and no ACTIVE `speedrun` session. Set Seed races and sessions never hide a page. While a page is not public, it answers `public: false` with `graph_json` null, no runs and empty stats (`best_igt_ms` and `median_igt_ms` null, `runs` and `players` 0); the seed number, category, origin, statuses and viewer block stay.

**Replayable.** A public seed is replayable in Set Seed unless one of these holds. The first one that holds, in this order, gives `not_replayable_code` and `not_replayable_reason`:

| Code               | Reason                                                                                  | When                                                                                                 |
| ------------------ | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `in_progress`      | `A blind run on this seed is still in progress.`                                        | The page is not public.                                                                              |
| `excluded`         | `An admin excluded this seed from Set Seed: <reason>`                                   | An admin excluded the seed (see Admin exclusion).                                                    |
| `old_game_version` | `Built for an older version of Elden Ring: it no longer works with the current game.`   | `Seed.created_at` (when the pool scan added the seed) is before `SET_SEED_MIN_SEED_DATE` (when set). |
| `old_category`     | `Built for an older version of <Pool> (<seed layers> layers, <pool layers> today).`     | `total_layers` differs from the pool config's `layers_count`.                                        |
| `purged`           | `Its files were deleted from the server to free space: it can no longer be downloaded.` | The seed's zip (`folder_path`) is gone.                                                              |

**Response.** `SpeedrunSeedResponse`:

- `category` and `category_name` come from `seed_category`: the pool's own at its current layer count, else `<pool>@<layers>` named `<Pool> (<n> layers)`, whether that count is archived or not. An old 25-layer Standard seed linked from an old race page still has its page, its runs and its name.
- `origin` is where the seed was first played: its earliest blind race (mode not `set_seed`, RUNNING or FINISHED, by start, else creation), with `race_id`, `race_name`, `daily_date` and `played_at`; without one, the earliest `speedrun` session's creation (race fields null); null when only replays were run on it.
- `runs` are every counted run on the seed (`load_counted_runs(seed_id=...)`: the board rules, plus layer counts missing from `archived_layers` and seeds added before `SPEEDRUN_BOARD_START_DATE`), blind and replay, every run type, Deathless or not, excluded seed or not, by time. Each player's best run is ranked (shared ranks as on the boards) and their other runs have `rank` null. A row is a board row plus `run_type`, `ranked` and the run's `zone_history`, loaded for this seed's runs only.
- **Unranked runs.** The list also holds the finished participants of finished races that count on no board: on a seed that was SEEN when drawn, or a community race reset after its start or re-rolled without a seed report (`load_unranked_runs`, the complement of `counts_on_boards_clause`; banned users out, disqualified and unfinished participants are not finished), so a seed only such races played still shows who played it. They have `ranked: false` and `rank` null (a seed in a training pool has no page, so none of these runs sits in one), sort by time among the others, never take a place and never shift a ranked run's place, and carry a `zone_history` like any run. Only this endpoint merges them in: the boards, the WR band, record histories, the `/summary` record, the purge's top-N and Most practiced seeds read `load_counted_runs` and never see them. `ranked` is true for every other run.
- `stats` are the best time, the median time (the lower middle on an even count, so always a real run's time), the run count and the player count over every listed run, unranked ones included.
- `excluded_reason` is the admin's reason while the seed is excluded, `protected_by` the number of players protecting it, `pool_config` the pool's settings and `graph_json` the map (null while not public).
- `protectable` says whether a protection would keep the seed's files: false when `not_replayable_code` is `purged`, `old_game_version` or `old_category` (the files are gone, or the seed can never be replayed again), true otherwise, `excluded` and `in_progress` included (an admin may restore the seed; the blind runs end).

**Kept reasons.** `kept_reasons` lists why the seed's files are kept, in this order, each only when it holds:

1. `Seed of the current <Pool> pool`: the seed is not DISCARDED.
2. `Top <N> seed of <category name>`: among the `SET_SEED_KEPT_TOP_SEEDS` seeds of its category with the best times on the Set Seed board (`top_seed_numbers`, read from the cached `speedrun:runs`, so it can lag by one cache TTL). Seeds excluded from Set Seed still rank here, though the board drops them: an admin may restore one, while a purged zip can be rebuilt only when the current generator still reproduces its graph (`tools/regenerate_seed.py`, see `docs/SEED_PIPELINE.md`). Seeds that can never be played again (`old_game_version`, `purged`) take no place, and neither do seeds added before `SPEEDRUN_BOARD_START_DATE`, whose runs are on no board.
3. `Protected by <n> player`, or `players` from 2 on.
4. `Played in the last <D> days`: the latest race (finish, else start, else creation) or solo session (finish, else creation) on the seed, of any mode and status, is less than `SEED_PURGE_GRACE_DAYS` days old, or the seed is in use now (a race in SETUP or RUNNING, or an ACTIVE solo session, on it, however old).

`retention_reasons` builds them from the facts `load_retention_facts` loads for any number of seeds at once. An empty list means nothing keeps a DISCARDED seed's files.

**Protection.** `PUT /api/speedrun/seeds/{seed}/protection` (logged in, not banned) keeps a seed's files: never on a seed that is not `protectable` (409 with its `not_replayable_reason`, e.g. the `purged` one), only by a player with a finished run on the seed, a FINISHED participant of a FINISHED race of any mode or a FINISHED `speedrun` or `set_seed` solo session that is not invalidated (403 "Only players with a finished run on this seed can protect it"), at most `SEED_PROTECTION_LIMIT` seeds per player (409 "You already protect 3 seeds", with the setting's value: "1 seed" for a limit of 1), with no expiry. Protecting a seed already protected answers 200 and takes no second slot. `DELETE` on the same path removes the protection and frees the slot (idempotent too). Both answer the viewer block. Protections live in `seed_protections`, one row per player and seed.

**Viewer.** The page's `viewer` is null for a logged-out visitor; otherwise `can_protect` (the viewer has a finished run on the seed, as the protection rule counts it, and is not banned, whatever their quota or the seed's `protectable`), `protected`, `protected_seeds` (the seed numbers the viewer protects, oldest protection first) and `protection_limit`.

**Admin exclusion.** `PUT /api/admin/seeds/{seed}/set-seed-exclusion` with `{"reason": "..."}` (1 to 500 characters, trimmed; 422 otherwise) excludes a seed from Set Seed: it is no longer replayable, its runs leave the Set Seed boards and stay on Random Seed, and the page shows `excluded_reason`. The time, the reason and the admin are stored on the seed (`set_seed_excluded_at`, `set_seed_excluded_reason`, `set_seed_excluded_by_id`); excluding it again replaces them. `DELETE` on the same path lifts the exclusion. Both answer 204 and drop the speedrun caches, so the boards change at once.

**Caching.** The seed page is not cached, so a finished solo run, a protection or an exclusion shows at once; only its top-seed reason reads the cached run list.

**The web page.** `/speedrun/seed/<seed_number>` (`web/src/routes/speedrun/seed/[seed]/`, components `Seed*.svelte` in `web/src/lib/components/stats/speedrun/`) loads the endpoint above; an unknown seed shows the site's not-found page ("Seed not found"), an ambiguous prefix the same page asking for more of the seed ID, and any other failure the error page. It reuses the finished race page's layout (fixed-height, the runs rail stacked above the map on phones, where it holds at most 40% of the screen height and scrolls in place, as on race and Daily Seed pages, so the title and the card stay on the first screen), without Highlights or chat:

- **Runs on this seed**, the left rail: the race page's `Leaderboard` in finished mode, one row per run in time order (keyed by `run_id`, colored by position), with a Blind, Replay or Unranked chip (its `runKinds` prop; Unranked is the `ranked: false` runs), the death count and the loadout. Rows show the server's `rank` (its `ranks` prop), not their position: equal times share a place, and a player's slower runs have none and are dimmed like the boards' obsolete rows; an unranked run has no place either but is not dimmed (its chip, titled "Seen seed, reset or re-rolled race: counts on no board", says why). A click ticks one run (its path alone on the map), Ctrl+click compares several, as on race pages. `?run=<run_id>` ticks that run on arrival; an id that is not listed ticks nothing. A public seed without any finished run says "No finished run on this seed yet." and still shows its map. With exactly one run ticked, the bar of the Map / Replay toggle links that run's own page: "<player> played it in <race name>" (the race), "in the Daily Seed of <day>" (the day, its UTC rotation date) or "solo" (the session), through `speedrunRunHref`; nothing while several runs are compared.
- **Header**: "Seed <n>", then "<category name> · first played in <origin race> on <date>" (the race or the day linked) or "first played solo on <date>", the share button and the status chip, "Replayable" or "Not replayable". The chip's tooltip (hover, or keyboard focus) gives the reason when the seed is not replayable; otherwise "Files kept" and the kept reasons joined by " · ", or "Files may be purged. Protect this seed to keep them." when nothing keeps them.
- **Play this seed in Set Seed**, the card in place of the race rules card: how replays count ("<category name> · Set Seed" board, never Random Seed), then "Play solo" (the rules stay in the Start a run window, the board's Rules and the download windows, not here), for organizers and admins "Create race" (see "On the web" under Starting a ranked run), and "LiveSplit splits" (for everyone, the seed's splits file; see `docs/LIVESPLIT.md`). Below a divider, for a logged-in viewer who can act on it only (one with a finished run on the seed, or one who protects it): "Protect this seed" with the quota ("You protect <k> of your <limit> seeds.") and a Protect or Unprotect button; a viewer without a finished run gets no row, and at the limit the button is disabled and the viewer's protected seeds are listed as links. A protection reloads the seed, so the chip's kept reasons follow. On a seed that is not replayable the card holds its title and the reason only; the protect row stays only for a viewer who already protects the seed, whose Unprotect frees the slot.
- The Map / Replay toggle (`MetroDagFull` with the layer comparison under it, `RaceReplay`), the stats row (best time, median time, runs with the replay count, players) and the category card (`PoolSettingsCard`).
- **Admins** get a reason field and "Exclude from Set Seed", or, on an excluded seed, "Excluded from Set Seed: <reason>" and "Restore"; the page reloads the seed after either.
- **Not public**: the header and its chip, and "This seed's map opens once every blind run on it is over." in place of the rail and the map.

Links to the page come from `web/src/lib/speedrun.ts`: `seedPageHref(seed, runId?)` builds it (`?run=` when a run is given); `speedrunSeedHref(run)` is a board run's seed page focused on that run; `speedrunRunHref(run)` is a run's own page (a Daily Seed's day, a race, or a solo session); `raceSeedPageHref` (a finished race, or a Set Seed race at any status) and `sessionSeedPageHref` (a Set Seed session, or a Speedrun session no longer active; never a `normal` session) say when a race or solo page should link its seed. They only spare links to pages that would still be hidden: the server's public rule stays the guard. Race and session responses carry `mode` on the web types too (`RunMode`).

Where the links appear: the WR seed band (the seed number, to the seed page focused on the record run), the board table (the seed cell is the keyboard-reachable link; a click anywhere else on a row navigates to the same page through `goto`, except on the player link or any other link or button, with Ctrl, Cmd or Shift held, or when it ends a text selection), and the `Seed <n>` badge of the race, daily and solo session pages, which is a link only when `raceSeedPageHref` / `sessionSeedPageHref` return one (a running blind race or an active Speedrun session shows plain text). The seed status chip's tooltip opens on hover and on focus (so a tap shows it on a phone) and Escape blurs the chip to close it.

## Starting a ranked run

`POST /api/speedrun/solo` (logged in, not banned, 10 per minute; `services/training_service.py`) starts a ranked solo session and answers 201 with the same detail response as `POST /api/training`, which stays practice-only. The body is `{"pool": ...}` (Speedrun mode) or `{"seed": ...}` (Set Seed), exactly one of them (422 otherwise).

- **Speedrun mode** (`create_speedrun_session`): the pool must exist, be enabled and not be a training pool (404 "Unknown pool"). The seed is drawn by `draw_speedrun_seed` from the race pool, so the pool's floor applies (409 "No fresh seed right now") and a `training_*` seed is never used. The seed is CONSUMED at creation and never released: cancelling the session through `/api/training/{id}/abandon` (CANCELLED, no progress) leaves it CONSUMED, so cancelling cannot fish for a seed.
- **Set Seed** (`create_set_seed_session`): the seed is found as on the seed page (404 "Unknown seed", also for an unplayed seed; 409 "Ambiguous seed ID") and must be replayable when the run starts (409 with the `not_replayable_reason`). It consumes nothing and touches no seed status.
- **Reset (Set Seed only).** `POST /api/training/{id}/reset` (owner, not banned; `reset_set_seed_session`) restarts an ACTIVE Set Seed run from scratch on the pack already installed: the session keeps its id and mod token, so the player closes the game, resets, relaunches it and starts a New Game, without downloading anything. The relaunch is needed: the mod gives the care package's Ashes of War once per game launch (`items_spawned` in `mod/src/dll/tracker.rs`), so a character made in the same launch misses them (a race reset has the same limit), and a reset clicked in game on a save under 60 s of IGT would add a quit-out penalty to the new attempt. One conditional UPDATE on ACTIVE and `set_seed` clears the attempt (`igt_ms`, `death_count`, `zone_history` to SQL NULL, `current_zone`, `last_igt_change_at`), so a finish committed meanwhile stands (400 naming the status, as for a run that already ended). The cheat detections, an admin invalidation and `discord_notified_at` belong to the run and stay; no attempt count is kept. A mod still connected is closed with 1000 first, and the reset waits for its handler to tear down (`close_mod(..., wait=True)`, at most `TEARDOWN_TIMEOUT`), so a message it was writing cannot land on the cleared run. The mod reconnects after the close: it gets `auth_ok` and `race_start` again, and while the history is empty the server ignores the old save's event flags and zone queries, and refuses its status updates past 60 s of IGT ("Please start a New Game", `fresh_save_required`), as on a first run. A finish that a reset empties between its final-zone check and its update is dropped (the update requires a history), so no run reaches the boards without one. Spectators get the cleared progress (`leaderboard_update`) then an empty `zone_history` (`broadcast_session_reset`). Refused with 400 "Only a Set Seed run can be reset: start a new run instead" for a Speedrun-mode session (the attempt must stay blind) and a practice one; a finished run holds its time on the boards, so replaying the seed takes a new run. The session page shows a Reset button next to Abandon on the owner's active Set Seed run, behind a confirmation that says to close the game before confirming, then relaunch it and start a New Game.
- **Expiry.** `expire_speedrun_sessions` runs on every poll of the inactivity monitor (`services/inactivity_monitor.py`, 60 s): an ACTIVE Speedrun-mode session created more than `SPEEDRUN_SESSION_TTL_HOURS` ago becomes ABANDONED with `finished_at` set, its zone history kept and its seed left CONSUMED, and its connections get an `abandoned` status change. Without it a forgotten blind session would keep its seed page hidden forever. Set Seed and normal sessions never expire. Both sides are conditional UPDATEs on ACTIVE: the expiry never overwrites a finish, and a finish report landing after an expiry or an abandon is dropped (`_handle_finish_event`: the session stays ABANDONED, with no `finished` status change and no record check).
- **Anti-cheat.** Ranked sessions (`speedrun`, `set_seed`) get the race's checks in `TrainingModHandler`: the mod's debug flags are recorded in `training_sessions.debug_flags` with the Discord admin alert, and a forward IGT jump past wall-clock time (`last_igt_change_at`) is rejected as a wrong save. Normal sessions skip both. A detection shows on the session page (admins only) and in /admin's Cheat tab. See `CHEAT_DETECTION.md`.
- **In game.** The mod's overlay names a ranked solo run after its kind as the boards name it, "<pool> · Random Seed" (Speedrun mode: a blind run, which counts on Set Seed too) or "<pool> · Set Seed" (a replay) (`solo_run_name`, the `auth_ok` race name); a practice session shows the pool's name alone.
- **Mod version.** A ranked session refuses at auth a mod below protocol 1.9 (`RANKED_SOLO_MIN_PROTOCOL`; an absent protocol reads as 1.0), which would not report debug flags in a solo session: the `auth_error` tells the player to download the run's pack again, which carries the current mod. Practice sessions, races, Daily Seeds and events accept older mods as before (see "Protocol Version" in `PROTOCOL.md`).
- **Finish rule.** A ranked session's finish flag counts only when its zone history contains the seed's final boss node (graph node type `final_boss`; on a graph without one, older seed eras, any node of the highest `layer`): `reached_final_zone` in `websocket/handler.py`, checked by `_handle_finish_event` on the history as committed when the flag arrives (the fog gate into the final zone is recorded by the `event_flag` before the kill). Otherwise the finish is dropped: the flag is acked, the session stays ACTIVE (a Speedrun-mode one expires as usual), there is no `finished` status change and no record check, a `Finish dropped ... never reached the final zone` WARNING is logged, the mod gets an uncoded `error` ("Finish not counted: the final boss zone was never recorded. The admins were notified. Abandon the run from its page to start another.", `FINISH_NOT_COUNTED_MESSAGE`; a Set Seed run ends on "Reset the run from its page to play it again." instead, `SET_SEED_FINISH_NOT_COUNTED_MESSAGE`), which every mod version shows as status text (the mod sends the finish flag once per DLL lifetime and otherwise would keep running with no word), and the private admin Discord channel gets a "Ranked finish rejected" alert (`notify_finish_dropped`: player, link to `/training/<id>`, "Solo · <pool> · Random Seed" or "Solo · <pool> · Set Seed", seed, IGT and the reason) so an admin can check the run, since a legit run can miss the node through a tracking gap. There is no admin "accept finish" action: the runner's way out is to abandon the run from its page and start another (or to reset a Set Seed run, see above). Practice sessions finish on the flag alone.
- **Session page.** While a `speedrun` session is ACTIVE the page stays blind: no Show Spoiler button, no full map and no structure-only map; the progressive map only once there is progress, and a line saying the map reveals itself as you play before that. The OBS Overlay button stays, and the overlay (`/overlay/training/<id>/dag`) follows the same rule: the progressive map while the session is ACTIVE (its status from the session's live connection), its usual full map once it is not. Both take the overlay's settings (`follow`, `maxLayers`, `fontSize`): `MetroDagProgressive` follows the runner through the full map's `FollowViewport`. The full map, the Replay and the ghosts come back as soon as the session is no longer ACTIVE (`trainingMapView` and `isBlindTrainingSession` in `web/src/lib/utils/training.ts` decide); a run that finishes on the open page loads its ghosts then. Once a ranked session is finished (and not invalidated), its stats bar adds the board place from `GET /api/speedrun/sessions/{id}/place`: "<category name> · Random Seed|Set Seed" over the ordinal place and "/<players>" ("4th/57") and a "PB" chip for the player's best, the whole stat linking to that board (`speedrunBoardHref`). A run that finishes on the open page asks 2 seconds later, and once more 5 seconds after that when the run is not on the cached boards yet (see the endpoint below); a session without a place shows nothing. `set_seed` sessions keep the Show Spoiler button. The session page, the Solo history rows and the active session card carry a `Speedrun · Random Seed` or `Speedrun · Set Seed` chip (`RunModeChip.svelte`), nothing on `normal` sessions.
- **Unfinished limit** (Speedrun mode only, checked before the draw so a refusal consumes no seed): a player with `SPEEDRUN_SOLO_UNFINISHED_LIMIT` Speedrun-mode sessions created within the last `SPEEDRUN_SOLO_UNFINISHED_WINDOW_HOURS` that are not FINISHED (ACTIVE, ABANDONED, CANCELLED, expired) gets 429 "You have <count> unfinished Random Seed runs in the last <H> hours (the limit is <N>). Finish a run, or try again in <wait>." (<count> is the actual number; <wait> is computed at request time, minutes rounded up, e.g. `5 h 12 min` or `12 min`: when enough of them have left the window; the Start a run window shows the detail as is). Finished runs, Set Seed sessions, other players' sessions and `0` never count or refuse; Set Seed solo and speedrun races have no limit, a speedrun race a `trusted` organizer starts alone included (see SETUP → RUNNING in `RACE_LIFECYCLE.md`): the role, granted and taken back by an admin, is the safeguard there.
- Both refuse with 409 "You already have an active solo session" while the player has any ACTIVE session, whatever its mode.
- `GET /api/speedrun/solo/quota` (auth required) answers the viewer's count against the unfinished limit, `{limit, unfinished, window_hours, frees_at}` (`unfinished_quota` in `services/training_service.py`, the rule the refusal above reads), or null when the limit is `0`. `frees_at` is null under the limit and, at or over it, when the session that matters leaves the window. The Start a run window asks it once the viewer is logged in and, in Random Seed with the Solo format, shows "Unfinished Random Seed runs in the last <H> hours: <count> of <limit>." once one start or none is left (not in a category closed to Random Seed): "At <limit>, new runs wait." with one left (gold), "Next start: <time>" (`formatScheduledTime`) at the limit (red), where Start solo is disabled until that time. A race, Set Seed and a failed lookup show nothing; the server still refuses a start over the limit.
- `GET /api/speedrun/sessions/{id}/place` (public, like the boards) answers where a finished ranked solo run's time places on its own board, `{category, category_name, sub, place, players, personal_best}` (`run_place` in `services/speedrun_service.py`): Random Seed for a blind run, Set Seed for a replay, the Deathless filter off and every run type; `place` is 1 + the other players whose best there is strictly faster (`place_of`, as in Recent PBs), `players` the players on that board, `personal_best` whether the run is its player's best there (lowest IGT, the earliest on a tie). Null for a session on no board (see Which runs are counted), e.g. a practice or unfinished one, an invalidated run, a banned player's, a replay on an excluded or too old seed. It reads the cached run list (`speedrun:runs`), so a run that just finished shows once its record check has put it there.
- `GET /api/speedrun/fresh-seeds?pool=<pool>` answers `{"fresh": bool}` (`has_fresh_speedrun_seed`; no auth; 404 "Unknown pool" for a missing, disabled or training pool, the pools `/solo` refuses), for the Start a run window. It and the summary below keep the API's default per-client limit (60 a minute).
- `GET /api/speedrun/seeds/{seed}/summary` answers what the Set Seed field shows while the player types: `seed_number`, `category`, `category_name`, `replayable`, `not_replayable_reason` and `record` (`igt_ms` and `user` of the seed's best counted run, the earliest on a tie; null without a run). No map. Lookup errors are the seed page's (404 "Unknown seed", 409 "Ambiguous seed ID"). A known seed with a blind run in progress answers 200 with `replayable: false`, its reason and `record: null`.
- `GET /api/speedrun/livesplit/{category}` (optional auth) answers what a LiveSplit file of a category is built from: `{category, category_name, total_layers, wr, pb}`, where `wr` is the fastest run of the category's Random Seed board (any run type, deathless or not) and `pb` the viewer's fastest one (null when logged out or without a run), each `{igt_ms, user, layer_entry_igts}`. `layer_entry_igts` maps a layer to the IGT of the run's first arrival on it (`build_leader_splits` over the run's zone history, revisits ignored, layer 0 included) plus the finish IGT under the seed's `total_layers`; the JSON keys are strings. `total_layers` is the key's `@<n>` suffix, else the pool's `layers_count`, else the record's seed layer count. A pool without counted runs (a training one included) answers 200 with no references; 404 "Unknown category" when the pool does not exist or the `@` suffix is not a number (`services/livesplit_service.py`). `RaceDetailResponse` and `TrainingSessionDetailResponse` carry `category`, the seed's category key (`seed_category`; null without a seed), so the web can ask for the matching file.
- `TrainingSessionDetailResponse` carries `invalidated` and `invalidation_reason` (public) and `debug_flags` (filled for an admin viewing `GET /api/training/{id}` only).
- **Invalidation.** An admin invalidates a ranked solo run with `PUT /api/admin/training/{id}/invalidation` (body `{"reason"}`, stripped, 1 to 500 characters; 400 "Only a ranked solo run can be invalidated" for a normal session, 400 "Already invalidated") and undoes it with `DELETE` on the same path (400 "Not invalidated"); both answer the session detail, with `debug_flags`, and drop the speedrun caches. `load_counted_runs` leaves an invalidated session out, so it leaves the boards, the seed page, the records and the overview at once, and comes back on cancel. The session page shows "Invalidated: <reason>" to everyone. See `CHEAT_DETECTION.md` ("Sanctions").

**Ranked races.** `POST /api/races` takes `mode` (`normal` by default). A **speedrun race** draws its seed like a Speedrun-mode run, through `draw_speedrun_seed` from the enabled race pool `pool_name` (a training pool answers 400 "Mode '<pool>' is not available", like a disabled one; 409 "No fresh seed right now" at the floor), and so do its rerolls (a refused reroll leaves the race on its seed). A **Set Seed race** names a played `seed` (full number or prefix), found and checked like a Set Seed run (404 "Unknown seed", 409 "Ambiguous seed ID", 409 with the not-replayable reason): it takes the seed's pool (a retired category's seed included), consumes nothing, is never rerolled (400 "A Set Seed race keeps its seed") and its deletion leaves the seed alone. A SETUP Set Seed race does not make its seed's page private: only a blind race does. The mode never changes. A **speedrun race cannot be reset** (`POST /api/races/{id}/reset` answers 400 "A speedrun race cannot be reset: create a new race instead", and the race page hides Reset Race), since the replay would count as blind; Set Seed races reset like normal ones (a reset community race in `normal` mode then counts on no board until a reroll with a seed report, see "Which runs are counted"). A speedrun race is thus the community race sure to count: a fresh seed, no reset, and a reroll only with a seed report (see "Which runs are counted"). The race page offers no Re-roll Seed on a Set Seed race, at any status. A reroll or deletion of a race still in SETUP, released or not, makes its unplayed seed SEEN whatever the race's mode (Set Seed aside; a reset race's played seed stays CONSUMED): its organizer, its runners and anyone reading the race's live data may have seen its map, so a speedrun race, a Speedrun-mode solo run, a Daily Seed and an event race's reroll never take it again. Normal races may, as a fallback stock (AVAILABLE seeds first while the pool is above its floor, SEEN seeds first at or under it, so a community race lands on one, and counts on no board, only when its pool runs low; their reroll may then draw a SEEN seed again), and event races are created as normal races and attached to their event later, so an event race can be created on a SEEN seed. The race records it: `Race.seed_was_seen` is set by a draw that takes a SEEN seed and cleared by one that takes an AVAILABLE seed (creation or reroll; `RaceResponse` carries it). Such a race counts on no board, even once attached to an event (`race_unranked_reason` and its SQL twin `counts_on_boards_clause`): the tournament runs as usual, its runs show as Unranked on the seed page, and the admin Races tab says "Seen seed: off the Speedrun boards until a re-roll." under the event slot (without "until a re-roll" once the race has started, since only a SETUP race can be rerolled). A reroll fixes it before the start: an event race's reroll takes an AVAILABLE seed (`race_draws_fresh_seeds`), which puts the race back on the boards. Attaching the race to its event does that reroll itself (`POST /api/admin/races/{id}/event`, through `apply_seed_reroll`, the Re-roll Seed button's own path: chat message, version bump, broadcasts) when the race is in SETUP on a SEEN seed and its seeds are not released yet, since nobody can hold its pack then; a race whose seeds are out keeps its seed for the admin to decide, and so does one whose pool has no AVAILABLE seed left (the attach goes through either way). See "Run mode" and "Seed Status" in `RACE_LIFECYCLE.md`.

**On the web.** Ranked runs start from the Start a run window and the seed page card (a Set Seed session's "Play Again" replays its seed directly, see below); the Solo page (`/training`) keeps its single Start button and practice sessions.

- **Start a run window** (`SpeedrunStartModal.svelte`, the OBS overlay window's look), opened by the board toolbar's "Start a run" (or by the WR seed band's "Play seed", in Set Seed mode on the record's seed), uses the board's words: Category, Subcategory **Set Seed | Random Seed** (the board's order, Random Seed chosen on opening), Format **Solo | Race** (shown to organizers and admins only, everyone else plays solo). Category shows the board's category, the one Random Seed draws from; in Set Seed it shows the seed's category once the lookup answers (replayable or not), and the board's again when the field holds no known seed. On a retired category (an archive `<pool>@<layers>` always is) it asks nothing and shows "Random Seed runs are closed for this category.", as it does when `fresh-seeds` answers 404; otherwise it asks `fresh-seeds` once on opening, and `false`, or any other failure, shows "No fresh seed right now". Either way the action is disabled, for Race too since a speedrun race draws under the same floor. Set Seed has a Seed ID field, with a "WR" button beside it when the board shown has a record whose seed can be replayed (`record_seed.replayable`): it types that seed in (the board on screen decides, Set Seed or Random Seed, its filters included, none while it loads or when the record seed cannot be replayed, which only a Random Seed board or an archive can show). The field is checked as typed through the summary endpoint: nothing under 6 characters, then 300 ms after the last keystroke, a response to an older keystroke dropped. It shows the server's "Unknown seed" or "Ambiguous seed ID", the not-replayable reason, or "✓ Replayable · WR <time> by <player>" (no WR part without a run), and enables the action only on a replayable seed. An explanation line per subcategory and format follows, naming the board the run ranks on (in Set Seed, the Category row's category, the board's while the field holds no known seed), then the rules. "Start solo" posts `/api/speedrun/solo` (`{"pool"}`, or `{"seed"}` with the full seed number) and opens `/training/<id>`, or shows the refusal in the window until the subcategory, the format or the Seed ID changes; "Create race" opens `/race/new?mode=speedrun&pool=<category>` or `/race/new?seed=<seed>`. Logged out, "Login with Twitch" replaces the action and brings the viewer back to the board. `/speedrun?start=set&seed=<n>` opens the window in Set Seed mode with the seed typed in, `/speedrun?pool=<pool>&start=random` in Random Seed mode over that pool's board (`parseStartRun` in `web/src/lib/speedrun.ts`); the page reads the keys once and drops them from the URL, the board's own keys staying.
- **Seed page card**: "Play solo" starts a Set Seed solo run on the seed and opens its session page (a refusal shows under the buttons); "Create race" links `/race/new?seed=<n>`. A logged-out viewer gets "Login with Twitch" (back to the seed page).
- **Session page**: once the owner's ranked run is over and they have no active session, a Speedrun-mode session's "New Run" opens the Start a run window in Random Seed mode on the run's pool (`startRandomRunHref`), the one a new run draws from, and a Set Seed session's "Play Again" starts a new Set Seed run on the same seed, as the seed page's "Play solo" (a refusal shows in the page's error banner). A practice session's "New Run" keeps leading to the Solo page.
- **`/race/new`** reads `seed`, `mode` and `pool` (`parseRaceNewParams`) when it opens, and again when a link to it with other parameters reuses the page (the navbar's Create Race from a Set Seed form gives a plain form back). Without a seed, a **Speedrun race** checkbox, last of the Advanced options (folded by default, so community race organizers do not meet it; the folded trigger's summary grid shows a "speedrun" entry, checked with the option on; its hint: "Always a fresh seed and no reset, so the race counts on the Speedrun boards; a seed re-roll asks for a reason, sent to the admins. The game modes above then count only the fresh seeds a speedrun race can draw."), off by default, on with `mode=speedrun`; `pool` preselects that pool when it has seeds, the first pool with seeds otherwise. A pool's seeds are the ones the race could draw: AVAILABLE and SEEN ones for a normal race (the public `GET /api/pools` gives both counts), the AVAILABLE ones above the pool's speedrun floor with the Speedrun option on (`GET /api/pools` gives the floor in force as `speedrun_floor`), since the server refuses a speedrun draw at the floor; the tabs, "N seeds available" and Create Race follow the option. With the option on, the heading reads "Create Speedrun Race" and the race name's placeholder names the selected game mode ("e.g. Standard Grinding"; "e.g. Sunday Showdown" otherwise). A pool at its floor reads "No fresh seed right now" in place of the count, and with no pool above its floor the form says "No fresh seed right now in any game mode." With the option off, a selected pool at or under its floor that holds SEEN seeds, which a normal race then draws first, gets "Low on fresh seeds right now: this race would get a seed another race gave up, whose map may be known, so it would not count on the Speedrun boards." under its count. With a seed, the heading reads "Create Set Seed Race" with a "Seed <n>" tag on its right (styled like a race page's seed tag: the seed's full ID linked to its page once the lookup answers, the URL's ID unlinked before that or when it fails), the race name's placeholder names the seed's category, and a gold banner: the seed's category, "Change seed" (back to `/speedrun?pool=<category>&start=set&seed=<n>`), "Runners may already know this seed. Times count on the <category> · Set Seed board only." and the rules. The mode grid gives way to "<category> · set by the seed" and the Speedrun option leaves the Advanced options, the pool card (when the pool is listed) and "Seed <n>, fixed: no reroll". An unknown or not replayable seed shows the server's text in the banner and disables Create Race. The form sends `mode` (`set_seed` with the full `seed`, else `speedrun` or `normal`); everything else on it is unchanged.
- **Marks.** A speedrun or Set Seed race shows a `Speedrun · Random Seed` or `Speedrun · Set Seed` chip (`RunModeChip.svelte`, the solo pages' chip: outside the speedrun page it names both the context and the subcategory) next to its seed badge on the race page and next to the deathless tag on race cards (the narrow card of the `/speedrun` side column reads `Random` or `Set Seed`, its `short` option, see The page). The navbar lights Speedrun, not Races or Solo, on the page of a speedrun or Set Seed race and of a ranked solo session: the page sets `navSection.speedrun` (`web/src/lib/stores/navSection.svelte.ts`) while it shows one, since the layout otherwise reads the item from the path. The activity rows of a profile, the dashboard and the admin Activity tab (`ActivityList.svelte`) carry the same chip after the race's or session's name, from the `mode` of each race, organizer, caster and solo item of the activity endpoints (Daily Seed items have none). Joining a Set Seed race from its page asks first, in the page's confirm dialog: "Set Seed race: other runners may have practiced this seed". The invite page (`/invite/<token>`) shows the same line above Accept Invite for a Set Seed race (`GET /api/invite/{token}` carries the race's `race_mode`).
- **Listings.** The home page and `/races` list normal races only, in their live, upcoming and finished sections (`GET /api/races?mode=normal`). The dashboard's Races to Join and the navbar's Races badge drop the other modes on the client side from `GET /api/races/joinable`, which still returns every mode. A running or scheduled speedrun or Set Seed race is listed on `/speedrun` instead, at the top of its side column (see The page), besides the Discord announcement of a public open race (in the speedrun channel when one is set, see `DISCORD_BOT.md`) and the dashboard's Active Now for its organizer and runners.
- **Rules.** One list for every run, `RUN_RULES` in `web/src/lib/rules.ts`: glitchless; quit-outs allowed (2-second penalty each); no other mods, only SpeedFog; skips allowed within a zone; no sequence break, reaching a zone other than through its fog gate; LiveSplit allowed only without SoulSplitter (the rule states no reason; SoulSplitter writes the game timer, see `docs/LIVESPLIT.md`). `SpeedrunRules.svelte` renders it in the board's Rules popover ("Speedrun rules"), the Start a run window and the Set Seed race banner; the download window of races and Daily Seeds ("Before you race") and the help page's race rules render the same list.

## Open Graph

Sharing `/speedrun` or `/speedrun/seed/<n>` unfurls a card rendered by the server, like race, daily and event pages: nginx routes known crawlers to `GET /api/og/speedrun/meta` and `GET /api/og/speedrun/seed/{seed}/meta` (`deploy/speedfog-racing.nginx.conf`), whose tags point at `GET /api/og/speedrun.png` and `GET /api/og/speedrun/seed/{seed}.png`. The cards (`speedrun_board.svg.j2` and `speedrun_seed.svg.j2`, built in `services/og_image.py` from `SpeedrunBoardCard` and `SpeedrunSeedCard`) carry a gold "Speedrun" badge and the record of what the link shows: its holder's avatar and name, "Blind" or "Replay" and the UTC day it was set, the time in gold on the right. A long name steps down so it never runs into the time.

- **Board.** The crawler's fetch keeps the shared link's query string, so the stub reads `pool`, `sub`, `deathless` and `types` as the page does (an unknown value falls back to its default; `obsolete` and `view` are ignored, they do not change the record) and describes that very board: "Set Seed" or "Random Seed" (then "· Deathless"), the category, the world record and how many players rank; the footer names the record's seed. A bare `/speedrun`, or an unknown pool, shows the first category, as the page does. An empty board reads "No run yet". The tags' URLs carry the resolved pool and the non-default filters only, as the page writes its URL.
- **Seed page.** The seed's category, "Seed <n>", the record (the best counted run, the one the Set Seed field's summary shows) and, in the footer, the page's run and player counts (unranked runs included) and "Replayable" or "Not replayable". Without a counted run the card has no record: it reads "No finished run yet" over zero counts (a blind run in progress, nothing finished), or "No ranked run yet" over the counts when the page lists unranked runs only (a seen seed, a reset race).

Without any counted run (board) or for an unknown or ambiguous seed, the stub falls back to the site's generic tags and image. PNGs are cached on disk under `og_cache_dir` per what they show, and for five minutes by clients; the stubs for a minute.

**Speedrun floor.** Every speedrun seed draw (`seed_service.draw_speedrun_seed`) is refused with "No fresh seed right now" (`SpeedrunFloorError`) when the pool has `<= floor` AVAILABLE seeds, a reroll's current seed left out of the count. SEEN seeds never count and are never drawn. The floor also shapes a normal race's draw: AVAILABLE seeds then SEEN ones while the pool is above it, SEEN seeds then the AVAILABLE reserve at or under it (see "Draws" in `RACE_LIFECYCLE.md`). The floor is `Pool.speedrun_floor` when set, else `SPEEDRUN_DEFAULT_FLOOR`; `has_fresh_speedrun_seed` answers whether a draw would succeed. Admins set it per pool through `PATCH /api/admin/pools/{name}` (`speedrun_floor`: an integer `>= 0`, `null` clears the override; omitted leaves it alone); `GET /api/admin/pools` returns it with `speedrun_floor_effective`, and the public `GET /api/pools` gives that value in force as `speedrun_floor` (the race form reads it; `effective_speedrun_floor`). A rescan never overwrites it. The admin panel's Seeds tab shows it as a "Speedrun floor" field on each race pool's row (empty means the default, shown as the placeholder), saved through that PATCH when the field changes. A value that is not a whole number 0 or more is refused in the field ("Enter a whole number, 0 or more.") with no request (`parseSpeedrunFloor`); a server refusal shows under the field, which goes back to the stored value. The draw does not change the seed's status: callers consume it. The picked seed's row stays locked until the caller's commit (`FOR UPDATE OF seeds SKIP LOCKED`, PostgreSQL only), so two concurrent draws never get the same seed; the count does not see a concurrent draw's uncommitted pick, so simultaneous draws can take a pool under its floor by the extra draws.

**Purge.** `deploy/cleanup-seeds.sh` deletes a DISCARDED seed's zip only when these settings allow it (top seed, protected, recently played or in use, or added before the cutoff); see the retention section of `docs/SEED_PIPELINE.md`.

**Deploy.** The first production value of `SET_SEED_MIN_SEED_DATE` is `2026-09-01T00:00:00Z`, when the pools were regenerated for Elden Ring 1.17: earlier seeds carry a 1.16 `regulation.bin` that breaks Torrent on the 1.17 executable. Set it in the server's `.env` when this ships. The server's mod DLL (`MOD_DLL_PATH`, installed by `deploy/deploy-mod.sh`) must speak protocol 1.9 or newer before this server version ships: a ranked solo session refuses an older mod at auth, so with an older DLL every ranked solo run is refused (see "Order and rollback" in `deploy/README.md`).
